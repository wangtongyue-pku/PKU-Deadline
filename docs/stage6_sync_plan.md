评估日期：**2026-10-11**。范围：编程网格（`programming.pku.edu.cn`）的题集数据自动获取。

**本轮结论先行**：6C-1 只做了**公开资料与现有代码分析、模拟连接测试、方案设计**。**没有**登录任何账号、**没有**读取任何真实账户数据、**没有**复用任何浏览器会话、**没有**安装计划任务、**没有**写 HTTP 客户端。下面每一条都标注了「已实现」「模拟测试通过」「尚未验证」。

## 2. 数据获取路线的候选方案

### 方案 1：手动保存 JSON（已实现，推荐作为基础）

用户在浏览器打开课程页 → 另存 `?type=json` 的内容为本地文件 → 程序导入。

- **优点**：零凭据、零网络、零合规风险、完全不依赖平台是否改版（文件在手就在）。
- **缺点**：每天要手动做一次，不能真正做到「自动」。
- **状态**：**已实现**（`load_grid_file` + `plan_sync` + `apply_sync_plan`），46 项离线测试。

### 方案 2：复用用户已建立的登录会话（技术可行，需授权，本轮未做）

用户在浏览器正常登录后，把**会话 Cookie** 交给本地程序；程序只读 `?type=json`。

- **优点**：不需要密码、不需要验证码识别、不绕过任何安全措施（登录完全由用户本人在真实浏览器完成）；请求量极小（每次同步 1 个 GET）。
- **缺口的诚实说明**：Cookie 本身是**等价于登录状态的凭据**。把它写进本地文件，等于把会话保管在磁盘上。因此：
  - 必须由用户显式提供，**不得**由程序自动从浏览器窃取（不去读 Chrome / Edge 的 Cookie 数据库，不装浏览器扩展）；
  - 只能存在本地受限文件（例如 `data/grid_session.json`，`data/` 已在 `.gitignore` 中），权限限当前用户；
  - 必须支持「一键清除会话」；
  - 过期后**只提示重新登录，绝不自动重登**。
- **尚未验证**：只带 Cookie 的 GET 是否被接受（可能需要额外请求头或 CSRF token）。用户可在浏览器 Network 面板自查，不需要把 Cookie 发给我。
- **状态**：**尚未验证**，且**实施前必须单独授权**。

### 方案 3：自动登录（用户名 + 密码或 IAAA 流程）

- **状态**：**不支持**。
- 理由：① 与第五阶段已固定的约束直接冲突（不做验证码识别、不保存密码、不绕过认证）；② IAAA 存在手机令牌 / 人脸采集等机制，自动化在技术上不可靠；③ 唯一已知的现成实现（`VSC_ProgrammingGrid`）把门户密码**明文写进编辑器配置**，这正是本项目明确拒绝的做法。
- 如果将来用户坚持要自动化登录，需要先解决「凭据如何安全保存」这个独立问题（Windows 凭据管理器 / DPAPI），并且**仍然**受平台条款约束。

### 方案 4：询问学校是否有官方导出 / 接口

- **状态**：**尚未验证**（未联系任何校方单位）。
- 这条路如果成立，会同时解决合规性与稳定性问题，且不需要本项目做任何自动化。**建议用户在方便时询问一次**，成本很低。

### 方案比较

| 维度 | 1 手动 JSON | 2 复用会话 | 3 自动登录 | 4 官方渠道 |
| --- | --- | --- | --- | --- |
| 真能「自动」吗 | 否 | 是（在会话有效期内） | 是 | 视情况 |
| 凭据暴露 | 无 | **有**（会话等价登录态） | **高**（密码） | 低 |
| 合规风险 | 最低 | 需用户核对平台规则 | 高 | 最低 |
| 平台负担 | 无 | 每次 1 个 GET | 略高 | 无 |
| 页面改版影响 | 无（文件在手） | 有 | 有 | 无 |
| 验证码 / 多因素 | 不涉及 | 用户手动完成 | 需绕过（**不做**） | 不涉及 |
| 本项目实现成本 | 已完成 | 中 | 高 | 低（若存在） |
| 本轮状态 | **已实现** | 待授权 + 待验证 | **不支持** | 尚未验证 |

## 3. 同步架构设计（6C-2 / 6C-3 共用）

```text
用户点「立即同步」或定时触发
        ↓
[1] 取得原始响应          适配器（HTTP 客户端）或 本地文件
        ↓                   失败 → 明确异常，绝不返回空
[2] 解析 + 校验            ProgrammingGridJsonAdapter（已实现）
        ↓                   rejections / warnings → trustworthy=False
[3] 可信闸门               require_trustworthy()（已实现）
        ↓                   不可信 → 中止，不生成可执行方案
[4] 差异计算               plan_sync（已实现，只读）
        ↓                   new / unchanged / deadline_changed / possible_duplicate
[5] 变更预览               页面展示，等待用户确认（6C-2；尚未接线）
        ↓
[6] 写入 SQLite            apply_sync_plan → 第四阶段审核导入（已实现）
        ↓                   事务、revision 检查、历史、整批回滚
[7] 同步状态记录           sync_state（尚未实现，见下）
```

**分层规则**：抓取（[1]）与写库（[6]）必须分离。中间任何一步失败都不会修改数据库——这是 6A/6B 已经用测试固定下来的性质。

### 3.1 去重与幂等（已实现）

- 唯一依据是**平台 ID**（`course.problemlists[].id`），经 `external_key` → `notice_key` 变成 64 位哈希存入已有的来源键字段（`task_notices.notice_hash`）。
- **没有新增表、没有 schema 变更**：复用第四阶段已有的来源列，因此不需要 schema v4 迁移，也不会动用户现有数据库。
- 同一份响应重复导入 → 全部变成 `unchanged`（有测试）。
- 同一响应内出现重复平台 ID → **中止导入**（有测试）。
- 标题相同但平台 ID 不同 → 各自成为独立任务（有测试；真实数据里「期中试题（新）/（旧）」就是这种情况）。
- 标题相似但平台 ID 不同 → **不自动合并**。第四阶段的模糊匹配被收窄为「标题 + 课程完全一致」才提示，避免把「练习（1）…（6）」全部报成疑似重复。

### 3.2 绝不删除规则（已实现，硬约束）

**响应里没有出现的题集，不会被删除、取消或标记完成。** `plan_sync` 对未出现的记录**根本不生成提案**；任务只能由用户手动删除（第四阶段软删除 + 历史）。这条有针对性的测试（`test_set_missing_from_a_later_response_is_never_deleted`）。

### 3.3 登录失效检测（设计，尚未实现）

- 判据：响应 `status != "OK"`，或返回登录页 HTML（含 `loginwithcaptcha` 或跳转 SSO）。适配器已把非 `OK` 信封映射为 `SourceAuthRequired`，**不会**当成空课程。
- 行为：记录"需要重新登录"状态 → 页面显示提示 → **不重试、不自动登录**。
- 状态持久化需要新增一张小表（见 3.5）。

### 3.4 网络超时、重试与频率（设计，尚未实现）

| 项目 | 设计 |
| --- | --- |
| 超时 | 单次 20 秒（可配置 5–60） |
| 重试 | 仅对 `SourceUnavailable`（连接失败 / 5xx / 超时）重试；最多 2 次，退避 5s / 20s |
| 不重试 | `SourceAuthRequired`（重试无意义）、`SourceRateLimited`（会加剧限流）、解析失败（重试不会让格式变对） |
| 频率 | 两次真实请求之间强制最小间隔（建议 ≥ 1 小时）；每天默认最多 1 次；页面手动同步也受此约束 |
| 并发 | 用与提醒模块相同的 SQLite 事务抢占，防止网页与定时任务同时抓取 |
| 平台负担 | 每次同步只发 1 个 GET；不做轮询、不预取题集内页 |

### 3.5 同步状态与日志（设计，尚未实现）

需要一张新表记录状态（**这将是 schema v4**，按既有规则先 SQLite 在线备份、DDL 与 `user_version` 同事务、失败回滚）：

| 字段 | 用途 |
| --- | --- |
| `last_attempt_at` / `last_success_at` | 「上次成功时间」；定时任务据此判断是否已过期 |
| `last_status` | `ok` / `auth_required` / `unavailable` / `rejected` |
| `last_error_kind` | 只存**类别**，不存响应正文 |
| `last_source` | `session` / `file` |
| `next_due_at` | 「开机后是否错过计划」的判据 |

**日志脱敏规则（硬性）**：日志**只写**状态类别、条目数、耗时、时间戳。**不写**课程名、题集标题、平台 ID、URL 查询串、Cookie、响应正文。错误信息复用现有做法（只报异常类别，不回显外部正文）。

### 3.6 6C-2「一键同步」页面（设计，尚未接线）

新增页面区块（或独立页），流程：

1. 显示上次同步时间与登录状态；
2. 「立即同步」按钮 → 抓取 → 解析 → 可信检查；
3. 展示预览：新增 N 条、截止变化 M 条、无变化 K 条、无法解析 J 条（**J > 0 时整批暂停**）；
4. 逐条或批量选择 new / link / update / skip；截止变化必须单独核对原值与新值；
5. 单独最终确认 → 写入；
6. 写入后显示「已新增 / 已更新」的历史入口。

**已具备的部分**：3–5 所需的计算与写入已经实现并测试；缺的是**第 1 步的抓取**与**页面接线**。

### 3.7 6C-3「定时同步」方案（设计，本阶段不实施）

**推荐：Windows 任务计划程序 + 登录触发 + 到期检查**，而不是常驻进程或云服务。

| 项目 | 设计 |
| --- | --- |
| 触发 | 「登录时」触发 + 每天一次；程序内部判断 `next_due_at` 是否已过期 |
| 关机 / 休眠 | **不声称能同步**。开机登录后由上述到期检查补一次；不唤醒、不休眠恢复 |
| 命令 | `python -m pku_deadline_agent.grid_sync --once`（无 GUI 依赖，可被计划任务调用） |
| 权限 | 当前用户，不需要管理员；不写系统目录 |
| 登录失效 | 记录 `auth_required`，页面下次打开时提示；**不弹窗轰炸** |
| 重复创建 | 幂等依赖平台 ID（已实现）；同一天重复运行只会得到 `unchanged` |
| 重复提醒 | 提醒去重键是 `task_id + deadline_revision + lead_seconds`（第四阶段已实现），同步只会在**截止时间真的变化**时递增 `deadline_revision` |
| 安装 | **不自动安装**。需用户明确同意后，由我给出具体命令或由用户手动创建 |

**不采用**：常驻后台进程（关机即失效，且需要管理生命周期）、云服务器 / 复杂队列（违背「简单、个人本地」的项目定位）。

## 4. 仍需用户确认或操作的事项

1. **是否授权方案 2（复用会话）** —— 需要用户说明可以接受哪种提供方式。**不要**把 Cookie 发给我或贴进任何文档。
2. **自行验证一件事**（在浏览器里，不需要告诉我内容）：打开课程页 `?type=json` 时按 F12 → Network → 找到那个请求 → 看它的 Request Headers 里除了 Cookie 是否还有别的必需头（例如 `X-Requested-With`、CSRF token）。只看有没有，不要复制值。
3. **是否愿意询问学校**是否有官方导出 / 接口（方案 4）。
4. **是否确认平台规则允许**这种低频只读访问 —— 我未取得平台条款原文，不做判断。
5. **是否同意安装计划任务**（6C-3，本阶段不安装）。
